# L2 - Detailed Requirements

Each requirement traces to one L1 in [L1.md](L1.md) and lists the mocks in [`docs/mocks/`](../mocks/README.md) that show it. Acceptance tests are written before implementation and must carry a header comment naming the L2s they cover, for example:

```typescript
// Acceptance Test
// Traces to: L2-004, L2-005
// Description: Sign-in rejects a wrong password and locks after five failures
```

Conventions used below:
- **Today** in examples is Sun 25 Oct 2026, America/Toronto.
- **Viewport classes**: XS < 576px, SM ≥ 576px, MD ≥ 768px, LG ≥ 992px, XL ≥ 1200px. Layout changes happen at the design-system breakpoints (640, 768, 1024 and 1280px). Responsive acceptance tests run at 360, 600, 800, 1000 and 1280px.
- **Parent**: a signed-in account holder. **Co-planner**: a parent with edit access to someone else's party. **Viewer**: view-only access. **Guest parent**: someone who received an invitation and has no account.

## L2-001: Sign up with email and password
**Traces to:** L1-001
**Mocks:** pages/sign-up/default, invalid, submitting, error

A visitor can create an account with first name, email, password, postal code and an optional marketing opt-in.

**Acceptance Criteria:**
1. Given a visitor on the sign-up page, when they submit a first name, a valid email not already registered, a password of at least 10 characters that contains a number or symbol, and a postal code in the GTA, then an account is created in an unverified state, a confirmation email is sent within 60 seconds, and they are taken to the "check your email" page.
2. Given any required field is empty or invalid, when they submit, then no account is created, each invalid field shows an inline error beginning with how to fix it, the field is marked `aria-invalid="true"`, and an error summary linking to each field appears at the top and receives focus.
3. Given the email is already registered, when they submit, then the page says an account already exists and links to sign-in and password reset, and the response time and message are the same whether or not the address is verified (no account enumeration beyond this page's documented behaviour).
4. Given the form is submitting, when the request is in flight, then the submit button shows a busy state, fields are read-only and a second submission is not possible.
5. Given the marketing checkbox is unticked, when the account is created, then the parent receives no marketing email.
6. Given a password that appears in a known breached-password list, when they submit, then the password is rejected with "Choose a password that hasn't appeared in a data breach".

## L2-002: Sign in with third-party identity providers
**Traces to:** L1-001
**Mocks:** pages/sign-in/default

**Acceptance Criteria:**
1. Given a visitor on the sign-in page, when they choose "Continue with Google" or "Continue with Apple" and complete the provider's flow, then they are signed in to an existing account with the same verified email or a new verified account is created.
2. Given the provider returns an error or the visitor cancels, when they return to Giddy, then they see the sign-in page with a message and no account is created.
3. Given a provider sign-in, when the account is created, then the email is treated as verified and the parent is taken to family setup.

## L2-003: Email verification
**Traces to:** L1-001
**Mocks:** pages/verify-email/default, success, error; notifications/verify-banner/*

**Acceptance Criteria:**
1. Given an unverified parent, when they open the verification link within 24 hours, then the address is marked verified and they see the success page leading to family setup.
2. Given a link older than 24 hours or already used, when it is opened, then the "link has expired" page is shown with a button that sends a new link.
3. Given an unverified parent, when they use the app, then a persistent banner asks them to confirm their email, and sending invitations is blocked with an explanation until they do.
4. Given "Resend link" is pressed, when fewer than 60 seconds have passed since the last send, then no email is sent and the button says when it can be used again.
5. Given the confirmation email bounces, when the parent next opens the app, then a danger banner says the address could not be reached and links to change it.

## L2-004: Sign in with email and password
**Traces to:** L1-001
**Mocks:** pages/sign-in/default, invalid, submitting, error

**Acceptance Criteria:**
1. Given a registered parent, when they submit the correct email and password, then they are signed in and taken to the page they originally requested, or Home if none.
2. Given an incorrect email or password, when they submit, then the message "That email and password don't match" is shown without revealing which was wrong, and the entered email is kept.
3. Given 5 failed attempts for the same account within 15 minutes, when a 6th attempt is made, then sign-in for that account is paused for 15 minutes and the parent is told so; a successful password reset lifts the pause.
4. Given "Keep me signed in" is ticked, when the parent signs in, then the session lasts 30 days from the last activity; when unticked, it ends when the browser session ends.
5. Given the sign-in page loads, when it renders, then focus is in the email field and the email and password fields have `autocomplete="email"` and `autocomplete="current-password"`, and pasting into them is allowed.

## L2-005: Password reset
**Traces to:** L1-001
**Mocks:** pages/forgot-password/*, pages/reset-password/*

**Acceptance Criteria:**
1. Given a visitor on "Forgot password", when they submit any well-formed email, then the same confirmation is shown whether or not an account exists, and if one exists a single-use reset link valid for 30 minutes is emailed.
2. Given a valid reset link, when the parent sets a new password meeting the password rules and confirms it, then the password is changed, they are signed in on this device, and every other session for the account is ended.
3. Given the two passwords differ or the new one is too weak, when they submit, then inline errors and a summary are shown and nothing changes.
4. Given an expired or used link, when it is opened, then the "link has expired" page is shown with a way to request a new one.
5. Given the email service fails, when they request a link, then an error explains the email was not sent and the entered email is kept.

## L2-012: Party overview and readiness
**Traces to:** L1-003
**Mocks:** pages/party-overview/default, loading, empty, partial, error

**Acceptance Criteria:**
1. Given a party, when the overview loads, then it shows the countdown in days, date, time, venue, invited count, a readiness percentage, the booking status of each planned item (venue, entertainer, cake, food, loot bags) with price, the next three checklist tasks, RSVP counts, the allergy list, the budget summary and the co-planners.

4. Given the vendor-status service fails but the rest succeeds, when the overview loads, then only the bookings section shows a warning with Try again, and all other sections work.

## L2-022: Agent safety and grounding
**Traces to:** L1-004

**Acceptance Criteria:**
1. Given any prices, availability or vendor facts in a Giddy reply, when they are shown, then they come from Giddy's tool results for this request, not from the model's general knowledge.
2. Given a message tries to make Giddy ignore its rules, reveal another family's data, or perform an action without confirmation (prompt injection, including text inside vendor listings or reviews), when Giddy responds, then it refuses and does none of those things.

4. Given each conversation, when it is stored, then prompts, tool calls and results are logged with the party ID for 90 days for support and safety review, excluding payment data.

## L2-035: Budget tracking
**Traces to:** L1-009
**Mocks:** pages/budget/default, loading, empty, error

**Acceptance Criteria:**
1.
